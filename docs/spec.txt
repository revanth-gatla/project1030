# 16. REFERENCE RANGE ENGINE

This must be deterministic.

Given:

```text
Observed = 10.2
Reference = 13–17
```

calculate:

```text
BELOW
```

Given:

```text
Observed = 15
Reference = 13–17
```

calculate:

```text
WITHIN
```

Given:

```text
Observed = 18
Reference = 13–17
```

calculate:

```text
ABOVE
```

If reference range is missing:

```text
UNKNOWN
```

The LLM must NOT decide this.

The report's supplied range takes precedence.

Never silently substitute a generic medical reference range.


The comparison must be structured.

For every comparable parameter calculate:

```text
Previous value
Current value
Change
Direction
Previous range
Current range
Comparability
```

Examples:

```text
Hemoglobin
Previous: 11.2
Current: 10.2
Change: -1.0
Direction: DECREASED
```

Do NOT ask the LLM to perform arithmetic.

Python/backend logic must calculate it.

If units differ:

```text
NOT_COMPARABLE
```

unless a safe, explicitly implemented conversion exists.

Never blindly compare incompatible units.

# 19. AI SUMMARY

Only generate the AI summary AFTER deterministic processing.

AI should receive structured information such as:

```text
validated patient information
validated lab results
reference statuses
conflicts
comparison results
```

The AI should generate:

* important findings
* notable out-of-range values
* changes between reports
* detected inconsistencies
* missing information
* clarification questions

The summary must use cautious language.

Never produce:

```text
You have diabetes.
You have anemia.
Take medicine X.
Increase your dosage.
Stop medicine Y.
```

Instead use:

```text
The report shows a hemoglobin value below the reference range supplied by the report.
```

Always distinguish:

```text
Observation
Interpretation
Uncertainty
```

# 20. CLARIFICATION QUESTIONS

Generate approximately 3–5 useful questions when needed.

Questions should be based on:

* missing intake information
* conflicts
* ambiguous extracted data
* incomplete report information
* unclear medication/allergy information

Example:

```text

```

Questions are NOT medical advice.

---

# 30. AI EFFICIENCY

AI calls are expensive and slow.

Avoid unnecessary calls.

Preferred pipeline:

```text
ONE structured extraction call
        ↓
local deterministic processing
        ↓
ONE summary/clarification call when needed
```

Do NOT call the AI separately for every lab parameter.

Bad:

```text
Hb → AI
WBC → AI
Glucose → AI
Platelets → AI
```

Good:

```text
Whole report → ONE structured extraction
```

Then process locally.

---

# 31. CACHING / REUSE

Do not repeatedly process unchanged reports.

Store:

* report processing status
* extraction version
* model version
* prompt version
* content hash if practical

If the same report is processed again without changes, reuse the result.

Do not regenerate AI summaries unnecessarily.

---

# 32. IDEMPOTENCY

Processing the same report twice should not create duplicate data.

Use:

* unique identifiers
* content hashes
* processing states
* transaction handling

Example:

```text
same report
     ↓
existing processed result
     ↓
reuse instead of duplicate extraction
```


for authenticated production APIs unless there is a very specific justified reason.

---

# 72. AUTH SESSION SECURITY

Prefer secure, HTTP-only authentication cookies where architecture permits.

Cookies should use:

```text
HttpOnly
Secure in production
SameSite appropriate to deployment
```

Avoid storing sensitive authentication tokens in localStorage if an HTTP-only cookie architecture can be used safely.

---

# 73. OWNERSHIP SECURITY

Every patient-related endpoint must verify:

```text
patient.owner_user_id == authenticated_user.id
```

Never accept a patient ID and assume authorization.

This must be tested.

---

# 74. FRONTEND ROUTE SECURITY

Protected pages should require authentication.

But remember:

> Frontend protection is UX/security defense-in-depth. Backend authorization is mandatory.

---

# 75. RATE LIMITING

Protect:

* login
* registration
* AI processing
* report processing

from abuse.

Use a simple production-compatible approach.

Do not introduce Redis merely for rate limiting if a simpler solution is sufficient.

* model
* prompt version
* request duration
* failure
* token usage if available

Do not send the entire raw report again unless required.

# 77. PREMIUM UI/UX — JUDGE-ATTRACTING PRODUCT EXPERIENCE

The MedLens interface must feel like a polished, modern healthcare-data product — NOT a generic CRUD dashboard, admin panel, or chatbot.

The goal is:

> Simple on the surface. Powerful underneath.

The user should constantly feel:

> "I understand what MedLens found, I can see where it came from, and I decide what to do next."

## DESIGN PHILOSOPHY

Prioritize:

* user control
* clarity
* calmness
* trust
* intelligent interaction
* accessibility
* low cognitive load
* visual hierarchy
* fast comprehension
* professional healthcare/productivity aesthetics

Avoid designing for visual spectacle at the expense of usability.

Do NOT use excessive:

* gradients
* neon colors
* glassmorphism
* 3D effects
* decorative animation
* oversized marketing sections
* chatbot-like UI

Use subtle polish instead:

* refined typography
* generous spacing
* professional cards
* restrained borders and shadows
* meaningful icons
* clear status indicators
* smooth micro-interactions
* strong alignment and hierarchy

## LANDING / FIRST-USE EXPERIENCE

If a public landing page exists, keep it concise and product-focused.

Hero concept:

"Turn Medical Reports Into Structured, Traceable Insights"

Provide clear actions such as:

* Get Started
* Explore Demo

Visually communicate the pipeline:

Messy Information
→ Structured
→ Validated
→ Analyzed
→ Human Reviewed

Do not overwhelm first-time users with a long tutorial.

On first use, provide a simple choice:

* Create Patient
* Explore Demo

Do not force an onboarding wizard.

## APPLICATION NAVIGATION

Use persistent navigation.

Main navigation:

* Dashboard
* Patients
* Reports
* Analysis
* Review

Within a patient:

* Overview
* Intake
* Reports
* Lab Results
* Analysis
* Comparison
* Conflicts
* Questions
* Review History

Use active navigation states and breadcrumbs where helpful.

The user must be able to move freely between relevant sections.

## DASHBOARD EXPERIENCE

The dashboard should immediately answer:

1. What do I have?
2. What changed?
3. What needs attention?
4. What can I do next?

Include:

* patient overview
* recent patients
* recent reports
* pending reviews
* open conflicts
* clarification questions
* verification progress
* report/analysis activity
* quick actions

Quick actions:

* Add Patient
* Upload Report
* Paste Report
* Review Pending Items

Create a prominent "Needs Attention" area when actionable items exist.

Prioritize:

1. extraction failures
2. conflicts
3. low-confidence fields
4. missing important information
5. unverified extracted values

Do not create a fake health score.

## PATIENT WORKSPACE

Create a clear patient workspace with a strong header containing:

* patient name / identifier
* age
* sex
* latest report
* report count
* review status

Provide contextual actions close to the relevant information.

Do not force a sequence of pages.

The patient workspace should feel like a single coherent record rather than unrelated screens.

## REPORT UPLOAD EXPERIENCE

Make report ingestion highly intuitive.

Support:

* drag and drop
* Choose File
* Paste Report Text

Clearly communicate:

* supported formats
* maximum file size
* what will happen next
* that uploaded reports are treated as source data

Use clear visual feedback for selected files.

Validate files before processing.

## PROCESSING EXPERIENCE

Never make the application feel frozen.

Show real processing stages based on actual backend state:

* Uploading
* File validated
* Text extracted
* Extracting structured values
* Validating
* Normalizing
* Analyzing
* Generating insights
* Complete

Never display fake progress percentages.

If processing is asynchronous, allow the user to understand that processing is continuing.

On completion, do NOT automatically redirect.

Show:

"Report processed successfully."

Then provide choices:

* Review extracted data
* View findings
* Review conflicts
* Compare Reports
* View Source
* Open Patient Record

The user decides what happens next.

## LAB RESULTS EXPERIENCE

The main lab-results view should be compact and easy to scan.

Table columns should include:

* Parameter
* Value
* Unit
* Reported Range
* Status
* Source
* Review

Support:

* search
* filter
* sort
* sticky headers
* pagination where appropriate

Use expandable rows/cards for deeper information.

Default:

Hemoglobin
10.2 g/dL
Below reported range

Expanded:

* Original term
* Canonical term
* Reference range
* Source report
* Page/location when available
* Source text
* Confidence
* Extraction method
* Verification state

This is progressive disclosure.

## STATUS DESIGN

* BELOW
* WITHIN

## CONFLICT EXPERIENCE

* why it was flagged
* current status
* available actions

* Acknowledge
